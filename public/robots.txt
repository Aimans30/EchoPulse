# FIXED Sept 2026 — record scoping bug. The Disallow lines used to sit at the
# BOTTOM of the file, after the last `User-agent: Bytespider` block. In
# robots.txt, directives bind to the most recent User-agent record, so those
# three Disallows applied to Bytespider ONLY:
#
#   • /api/ was NOT disallowed for Googlebot, despite the comment saying it was.
#     Webhook and internal test endpoints (/api/dodo/webhook, /api/test-pipeline,
#     /api/crm-test, /api/slack-test) were all crawlable.
#   • /_next/ was blocked for Bytespider only. That is the one piece of luck
#     here: had it landed in the `*` group it would have blocked Googlebot from
#     every JS and CSS chunk and from /_next/image, which prevents Google
#     rendering the page at all.
#
# Disallow now sits inside the `*` record where it was always meant to be.
# /_next/ is deliberately NOT blocked for anyone: crawlers must fetch the JS,
# CSS and optimized images to render and rank the page.

User-agent: *
Allow: /
Disallow: /api/

# NOTE: /onboard and /pricing-matrix are private but are deliberately NOT
# disallowed here. Both set `robots: { index: false, follow: false }` in their
# own page metadata, and a robots.txt Disallow would stop Google ever crawling
# them — which means it can never SEE the noindex tag, so a URL discovered via
# a stray link can still surface as a bare result. The meta tag is the correct
# single mechanism for those two.
